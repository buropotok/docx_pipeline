Контракт парсера (Parser Contract) для DOCX Pipeline версии 2.15
1. Общие положения
Парсер (parser.py и вспомогательные модули) преобразует размеченный DOCX-файл в JSON-представление согласно схеме raw.schema.json версии 2.15. Входной документ должен быть предварительно обработан скриптом add_custom_attrs.py, который добавляет к корневым элементам и строкам таблиц атрибуты my:id с уникальными идентификаторами. Эти атрибуты являются единственным источником идентификаторов для соответствующих элементов; парсер не генерирует идентификаторы самостоятельно, а только извлекает их.

2. Пространства имён и атрибуты
Пространство имён для пользовательских атрибутов:
xmlns:my="https://translatefactory/schema/custom-id"

Атрибут идентификатора: my:id

Атрибут присутствует у следующих элементов:

<w:p>, являющийся корневым абзацем (непосредственный ребёнок <w:body> или внутри ячейки таблицы? – уточнение: для вложенных абзацев атрибут не проставляется, они идентифицируются локально).

<w:tbl> (корневая таблица)

<w:tr> (строки таблиц)

3. Правила идентификации
3.1. Корневые абзацы
Абзацы, находящиеся непосредственно в <w:body> (не внутри таблиц), должны иметь атрибут my:id вида p_<n>, где <n> – порядковый номер абзаца в документе (начиная с 1).

Парсер считывает этот атрибут и сохраняет его в поле id объекта абзаца в JSON.

Если атрибут отсутствует – парсер должен сообщить об ошибке (документ не размечен корректно).

3.2. Корневые таблицы
Таблицы, находящиеся непосредственно в <w:body>, должны иметь атрибут my:id вида tbl_<n>, где <n> – порядковый номер таблицы в документе (начиная с 1).

Атрибут сохраняется в поле id объекта таблицы в JSON.

3.3. Строки таблиц
Каждая строка <w:tr> внутри таблицы должна иметь атрибут my:id вида tbl_<n>.row_<m>, где:

tbl_<n> – идентификатор родительской таблицы.

<m> – порядковый номер строки в этой таблице (начиная с 1).

Атрибут сохраняется в поле id соответствующего объекта строки (в массиве rows).

3.4. Ячейки, вложенные абзацы и run'ы
Ячейки <w:tc> не получают отдельных атрибутов. Их идентификация осуществляется локально по индексу в строке (начиная с 1).

Абзацы внутри ячеек также не имеют атрибутов. Их идентификаторы генерируются парсером автоматически по правилу:
{id_ячейки}.p_{index}, где index – порядковый номер абзаца в ячейке (начиная с 1).

Run'ы внутри абзацев не имеют атрибутов. Их идентификаторы генерируются парсером локально для каждого абзаца по правилу:
{id_абзаца}.run_{counter}, где counter – сквозной счётчик run'ов внутри данного абзаца (начиная с 1). Поле parent_id в объекте run (опционально) может содержать идентификатор родительского абзаца.

4. Структура выходного JSON
JSON строго соответствует схеме raw.schema.json версии 2.15. Ключевые моменты:

Корневые объекты (абзацы и таблицы) располагаются в массиве content в том же порядке, в котором они следуют в <w:body>.

Каждый объект имеет поле type со значением "paragraph" или "table", а также поле id, взятое из атрибута my:id.

Абзац содержит:

p_style_id (из элемента <w:pStyle> или значение по умолчанию)

p_format (объект с переопределениями свойств, извлечённый из <w:pPr>)

runs – массив объектов run'ов, каждый с полями type, id, text (для текста), r_style_id, r_format и др.

Таблица содержит:

tblPr – свойства таблицы (границы, ширина, заливка и т.д.)

tbl_grid – массив ширин колонок

rows – массив объектов строк, каждый с id (из атрибута) и массивом cells

Ячейка (объект в массиве cells) содержит:

id – генерируется как {id_строки}.cell_{index}

tcPr – свойства ячейки (необязательно)

content – массив абзацев (каждый со своей структурой)

Run содержит:

id – генерируется как {id_абзаца}.run_{counter}

type – один из допустимых типов (text, tab, break, ...)

Для типа text: поле text

Для типа picture: поля file, relation_id, extent

r_style_id – идентификатор стиля символов (если есть)

r_format – объект с переопределениями форматирования

5. Обработка passthrough-элементов
Любые элементы <w:body>, не являющиеся <w:p> или <w:tbl> (например, <w:sectPr>, закладки, комментарии), игнорируются парсером и не включаются в JSON. Они остаются в оригинальном документе и не участвуют в пайплайне (но будут сохранены реконструктором).

6. Проверка и валидация
Парсер должен включать опциональную валидацию (DOCX_PIPELINE_VALIDATE_RAW=1), которая проверяет:

Наличие обязательных полей у каждого объекта.

Соответствие идентификаторов иерархической структуре (например, id строки должен начинаться с id родительской таблицы).

Уникальность id среди всех объектов одного уровня (корневые абзацы и таблицы – глобально, строки – в пределах таблицы, run'ы – в пределах абзаца).

7. Обработка ошибок
Если ожидаемый атрибут my:id отсутствует у корневого абзаца, таблицы или строки – парсер должен аварийно завершиться с сообщением об ошибке.

При обнаружении дублирующихся идентификаторов – ошибка.

При несоответствии структуры (например, ячейка без содержимого) – ошибка или предупреждение (в зависимости от настроек валидации).

8. Детерминизм
При одинаковом входном DOCX (с одинаковыми атрибутами) парсер должен генерировать идентичный JSON. Это обеспечивается детерминированным порядком обхода элементов и фиксированными правилами генерации идентификаторов для вложенных элементов (ячеек, абзацев, run'ов).

9. Пример
Входной XML (фрагмент):

xml
<w:body>
  <w:p my:id="p_1">
    <w:pPr>...</w:pPr>
    <w:r>...</w:r>
  </w:p>
  <w:tbl my:id="tbl_1">
    <w:tblPr>...</w:tblPr>
    <w:tblGrid>...</w:tblGrid>
    <w:tr my:id="tbl_1.row_1">
      <w:tc>
        <w:p>...</w:p>
      </w:tc>
    </w:tr>
  </w:tbl>
</w:body>
Выходной JSON (сокращённо):

json
{
  "content": [
    {
      "type": "paragraph",
      "id": "p_1",
      "p_style_id": "a",
      "runs": [...]
    },
    {
      "type": "table",
      "id": "tbl_1",
      "tblPr": {...},
      "tbl_grid": [...],
      "rows": [
        {
          "id": "tbl_1.row_1",
          "cells": [
            {
              "id": "tbl_1.row_1.cell_1",
              "content": [
                {
                  "type": "paragraph",
                  "id": "tbl_1.row_1.cell_1.p_1",
                  "p_style_id": "a",
                  "runs": [...]
                }
              ]
            }
          ]
        }
      ]
    }
  ]
}
10. Совместимость
Документы, не размеченные скриптом add_custom_attrs.py, не могут быть корректно обработаны парсером (отсутствие обязательных атрибутов приведёт к ошибке). Это требование должно быть отражено в документации пайплайна.

Данный контракт фиксирует поведение парсера и служит основой для его реализации и тестирования. Любые изменения в логике идентификации или структуре JSON должны отражаться в этом документе и сопровождаться обновлением версии схемы.
