ТЕБЕ ПЕРЕДАН JSON-ФАЙЛ donor.json, ПОЛУЧЕННЫЙ ПАРСИНГОМ WORD-ДОКУМЕНТА. Каждый текстовый run в этом файле имеет собственный реальный идентификатор run_id, например: p_6.run_1, p_6.run_2, p_17.run_4 и т.д.

ТВОЯ ЗАДАЧА:
Построить ОТДЕЛЬНЫЙ JSON fingerprint документа.

ВАЖНО:
- НЕЛЬЗЯ изменять donor.json.
- НЕЛЬЗЯ возвращать сокращённый результат.
- НУЖНО покрыть все абзацы donor.json, содержащие видимый текст.
- НУЖНО учитывать текстовые абзацы как на верхнем уровне, так и внутри таблиц.
- Работай только с видимым текстом.
- Пустые run, tab, break, cr не являются самостоятельными сегментами fingerprint, если не несут видимого текста.

================================================================
1. ЦЕЛЬ FINGERPRINT
================================================================

Fingerprint должен разделять текст документа на сегменты 4 классов:

- template_static — универсальная статика формы/бланка
- issuer_profile — данные учреждения / реквизиты / данные органа / представителей органа
- document_dynamic — данные конкретного экземпляра документа
- ambiguous — если уверенная классификация невозможна

Каждый сегмент должен иметь:
- id
- class
- role
- text
- sources
- evidence

================================================================
2. ФОРМАТ ВЫХОДА
================================================================

Верни JSON следующей структуры:

{
  "meta": {
    "source_schema_version": "...",
    "fingerprint_version": "2.2",
    "source_run_id_pattern": "p_<paragraph>.run_<n>"
  },
  "fingerprint": [
    {
      "paragraph_index": 0,
      "paragraph_id": "p_1",
      "segments": [
        {
          "id": "p_1.run_1",
          "class": "template_static",
          "role": "heading",
          "text": "ПАСПОРТ",
          "sources": [
            {
              "run_id": "p_1.run_1",
              "start": 0,
              "end": 7
            }
          ],
          "evidence": ["заголовок документа"]
        }
      ]
    }
  ]
}

================================================================
3. РОЛИ СЕГМЕНТОВ
================================================================

Допустимые значения role:

- field_label
- field_value
- heading
- issuer_name
- issuer_address
- issuer_contact
- issuer_requisite
- person_name
- person_id
- date
- registry_number
- note_header
- note_body
- signature_label
- signer_name
- signer_position
- seal_label
- seal_text
- other

Если ни одна роль не подходит уверенно, сгенерируй новую роль по контексту, семантике и смыслу документа и поясни свой выбор в evidence.

================================================================
4. БАЗОВЫЕ ПРАВИЛА КЛАССИФИКАЦИИ
================================================================

4.1. Метка поля и значение поля — это РАЗНЫЕ сегменты.

Пример:
"Тел.: 8 (727) 269 95 88"

должно стать:

1) "Тел.:" → template_static / field_label
2) " 8 (727) 269 95 88" → issuer_profile / issuer_contact

Если в одном run смешаны метка и значение, ОБЯЗАТЕЛЬНО разделяй их.

4.2. Пустое значение поля:
Если по структуре видно, что поле есть, а значение отсутствует, нужно создать отдельный document_dynamic сегмент с text = "" и соответствующим source-диапазоном.

4.3. Не добавляй отсутствующий текст.
Нельзя фантазировать. Разрешено только:
- разделять исходный текст на сегменты,
- объединять соседние текстовые run в один сегмент,
- выделять логически пустое значение, если это прямо следует из структуры.

================================================================
5. ABC-ТЕСТ КЛАССИФИКАЦИИ
================================================================

Для каждого сегмента задай 3 вопроса:

ВОПРОС A:
Может ли этот текст ПОЛНОСТЬЮ измениться при смене лица / экземпляра документа, при том же учреждении и том же бланке?
Ответ: ДА / НЕТ

ВОПРОС B:
Может ли этот текст ПОЛНОСТЬЮ измениться при смене учреждения, при том же типе бланка?
Ответ: ДА / НЕТ

ВОПРОС C:
Является ли этот текст универсальной частью формы?
Ответ: ДА / НЕТ / ЧАСТИЧНО

ПРАВИЛА:

- A=НЕТ, B=НЕТ, C=ДА → template_static
- A=ДА, B=любой, C=НЕТ → document_dynamic
- A=любой, B=ДА, C=НЕТ → issuer_profile
- A=НЕТ, B=НЕТ, C=ЧАСТИЧНО → сегмент нужно РАЗДЕЛИТЬ
- если данных недостаточно → ambiguous

ПРИОРИТЕТЫ ПРИ КОНФЛИКТЕ:
- document_dynamic > issuer_profile > template_static

ОСОБОЕ ПРАВИЛО:
Если текст является значением должности / ФИО / подписи конкретного подписанта данного экземпляра, это НЕ template_static. Это document_dynamic.

================================================================
6. ПРАВИЛА SPLIT (РАЗДЕЛЕНИЕ RUN)
================================================================

Сначала всегда применяй SPLIT, потом только MERGE.

Разделяй run, если внутри него есть:

6.1. Метка + значение
Пример:
"Тел.: 8 (727) 269 95 88"

6.2. Части разных классов
Пример:
"Город: АЛМАТЫ Республика: КАЗАХСТАН"

6.3. Части разных ролей
Даже если класс одинаковый, но роли разные, сегменты должны быть раздельными.

6.4. Явный текстовый маркер границы
Например:
- двоеточие
- подпись
- номер
- дата
- служебная метка

Точка split должна быть логически обоснована.

ВАЖНО:
После split:
- сумма длин текстов сегментов должна точно покрывать исходный видимый текст run
- все start/end в sources должны быть корректны
- не должно быть потери символов

================================================================
7. ПРАВИЛА MERGE (ОБЪЕДИНЕНИЕ RUN)
================================================================

После split можно объединять соседние текстовые run в один сегмент ТОЛЬКО если выполняются ВСЕ условия:

7.1. Они идут подряд в одном абзаце.

7.2. Между ними нет других видимых элементов.

7.3. Оба имеют type = "text".

7.4. Они образуют один логический сегмент одного класса и одной роли.

7.5. Объединение не приводит к смешению метки и значения.

7.6. Объединение не приводит к смешению разных классов.

7.7. Если у run разные char_style_id, объединение запрещено.

7.8. Если у run разные preserve/meta-параметры и это влияет на безопасную реконструкцию, объединение запрещено.
Если разница несущественна и по контракту допустимо объединение, происхождение всё равно должно быть полно отражено в sources.

ДОПОЛНИТЕЛЬНЫЕ ПРИЗНАКИ, ЧТО MERGE НУЖЕН:
- граница проходит внутри слова
- соседние run составляют одну статическую метку
- соседние run составляют одно значение

MERGE ЗАПРЕЩЁН:
- между разными абзацами
- между текстом разных классов
- между текстом разных ролей
- если merge ухудшает трассируемость или логическую точность

================================================================
8. ПРАВИЛА НУМЕРАЦИИ SEGMENT ID
================================================================

ЭТО КРИТИЧЕСКОЕ ПРАВИЛО.

Используй реальные исходные run_id из donor.json как базу для id сегментов.

8.1. Если run не разделялся и не объединялся:
id сегмента = исходный run_id

Пример:
run_id = p_6.run_1
id = p_6.run_1

8.2. Если ОДИН run разделён на несколько сегментов:
id каждого сегмента = <run_id>.<M>

где:
- <run_id> — реальный исходный run_id
- <M> — порядковый номер сегмента слева направо, начиная с 1

Пример:
исходный run:
p_6.run_1 = "Тел.: 8 (727) 269 95 88"

результат:
- p_6.run_1.1 = "Тел.:"
- p_6.run_1.2 = " 8 (727) 269 95 88"

8.3. Если НЕСКОЛЬКО run объединены в один сегмент:
id сегмента = <first_run_id>.1

где:
- <first_run_id> — run_id первого run в объединённой последовательности

Пример:
объединяются:
- p_10.run_3 = "ФИО "
- p_10.run_4 = "родителя"

итоговый сегмент:
- id = p_10.run_3.1

8.4. Если был и split, и merge:
id всё равно якорится к ПЕРВОМУ исходному run, от которого начинается итоговый сегмент.

Главное правило:
- id — это ЯКОРЬ сегмента
- полное происхождение сегмента читается через sources
- нельзя придумывать новые глобальные номера вроде run_4.1, если исходный run_id был p_6.run_1

ЗАПРЕЩЕНО:
- терять paragraph/run происхождение в id
- заменять реальные run_id искусственными numbering-схемами
- использовать абстрактные id, если в donor.json есть реальные run_id

================================================================
9. ПРАВИЛА SOURCES
================================================================

Каждый сегмент обязан иметь sources.

Каждый элемент sources:
{
  "run_id": "p_6.run_1",
  "start": 0,
  "end": 5
}

ПРАВИЛА:
- run_id — это реальный исходный run_id
- start — включительно
- end — не включая
- диапазон должен быть в пределах длины текста исходного run
- если сегмент получен merge, sources содержит несколько элементов в порядке склейки
- если сегмент получен split, sources отражает точный диапазон внутри исходного run
- табы/пустые run/переносы не использовать как source, если они не несут видимого текста

================================================================
10. ОСОБЫЕ ПРАВИЛА ДЛЯ ЗАГОЛОВКОВ, ПОДПИСЕЙ И ПЕЧАТЕЙ
================================================================

- Наименование документа обычно является сильным кандидатом на heading / template_static, если не содержит переменную часть.
- Если в заголовке есть переменная часть (номер, дата), выделяй устойчивую часть отдельно от переменной.
- "М.П." само по себе обычно signature/seal label, а не seal_text.
- Развёрнутый текст печати может быть issuer_profile или seal_text в зависимости от контекста.
- Должность конкретного подписанта экземпляра — document_dynamic.
- Универсальная служебная подпись/метка — template_static.

================================================================
11. ТРЕБОВАНИЯ К ПОЛНОТЕ
================================================================

Fingerprint обязан:
- покрывать 100% абзацев donor.json с видимым текстом
- сохранять порядок абзацев
- сохранять порядок сегментов внутри абзаца
- не пропускать текстовые абзацы внутри таблиц
- не выдавать демонстрационный или частичный результат

================================================================
12. ОБЯЗАТЕЛЬНАЯ САМОПРОВЕРКА ПЕРЕД ВОЗВРАТОМ
================================================================

ПРОВЕРКА 1 — COVERAGE
Все абзацы с видимым текстом включены в fingerprint.

ПРОВЕРКА 2 — SPLIT CONSISTENCY
Для каждого split-run:
- сегменты полностью покрывают исходный текст
- start/end корректны
- нет пропуска символов

ПРОВЕРКА 3 — MERGE CONSISTENCY
Для каждого merge:
- объединены только допустимые соседние text-run
- не смешаны разные классы и роли
- порядок sources корректен

ПРОВЕРКА 4 — ID CONSISTENCY
- id всегда якорится к реальному исходному run_id
- для split используется <run_id>.<M>
- для merge используется <first_run_id>.1
- не используются искусственные id без paragraph/run происхождения

ПРОВЕРКА 5 — ABC LOGIC
Каждый сегмент согласован с ABC-тестом и правилами приоритетов.

ПРОВЕРКА 6 — SCHEMA
- все обязательные поля присутствуют
- role входит в допустимый enum
- class входит в допустимый enum
- JSON валиден по fingerprint schema

Если хотя бы одна проверка не пройдена — исправь результат перед возвратом.

РЕЖИМ РАБОТЫ:
STRICT STRUCTURAL TRANSFORMATION.
Это не пример и не сокращённая выборка.
Это полное детерминированное построение fingerprint.
