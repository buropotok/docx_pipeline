ТЕБЕ ПЕРЕДАН JSON-ФАЙЛ donor.json, полученный парсингом Word-документа.

ЗАДАЧА:
Построить ОТДЕЛЬНЫЙ JSON fingerprint документа.

НЕ ИЗМЕНЯЙ donor.json.
НЕ СОКРАЩАЙ результат.
ПОКРОЙ ВСЕ абзацы с видимым текстом, включая текст внутри таблиц.

==================================================
1. ЧТО ТАКОЕ FINGERPRINT
==================================================

Fingerprint — это структурированное представление текста документа, где каждый текстовый фрагмент отнесён к одному из классов:

- template_static
- issuer_profile
- document_dynamic
- ambiguous

Каждый сегмент обязан иметь:

- id
- class
- role
- text
- sources
- evidence

==================================================
2. ФОРМАТ ВЫХОДА
==================================================

Верни JSON такого вида:

{
  "meta": {
    "source_schema_version": "...",
    "fingerprint_version": "2.2",
    "source_run_id_pattern": "p_<paragraph>.run_<n>"
  },
  "fingerprint": [
    {
      "paragraph_index": 0,
      "paragraph_id": "p_1",
      "segments": [
        {
          "id": "p_1.run_1",
          "class": "template_static",
          "role": "heading",
          "text": "ПАСПОРТ",
          "sources": [
            {
              "run_id": "p_1.run_1",
              "start": 0,
              "end": 7
            }
          ],
          "evidence": ["заголовок документа"]
        }
      ]
    }
  ]
}

==================================================
3. ДОПУСТИМЫЕ ROLE
==================================================

Используй только:

- field_label
- field_value
- heading
- issuer_name
- issuer_address
- issuer_contact
- issuer_requisite
- person_name
- person_id
- date
- registry_number
- note_header
- note_body
- signature_label
- signer_name
- signer_position
- seal_label
- seal_text
- other

Если точная роль неочевидна, используй other и поясни это в evidence.

==================================================
4. ABC-ТЕСТ КЛАССИФИКАЦИИ
==================================================

Для каждого сегмента мысленно проверь 3 вопроса:

A:
Может ли этот текст полностью измениться при смене лица / экземпляра документа при том же учреждении и том же бланке?
Ответ: ДА / НЕТ

B:
Может ли этот текст полностью измениться при смене учреждения при том же типе бланка?
Ответ: ДА / НЕТ

C:
Является ли этот текст универсальной частью формы?
Ответ: ДА / НЕТ / ЧАСТИЧНО

ПРАВИЛА:

- A=НЕТ, B=НЕТ, C=ДА -> template_static
- A=ДА, B=любой, C=НЕТ -> document_dynamic
- A=любой, B=ДА, C=НЕТ -> issuer_profile
- A=НЕТ, B=НЕТ, C=ЧАСТИЧНО -> ОБЯЗАТЕЛЬНО разделить сегмент
- если уверенности нет -> ambiguous

ПРИОРИТЕТ:
document_dynamic > issuer_profile > template_static

ОСОБОЕ ПРАВИЛО:
Если текст относится к конкретному подписанту, конкретной должности подписанта, конкретному ФИО, конкретной дате, номеру, персональным данным или значениям данного экземпляра — это НЕ template_static.

==================================================
5. ОСНОВНОЕ ПРАВИЛО РАЗДЕЛЕНИЯ
==================================================

СНАЧАЛА SPLIT.
ПОТОМ MERGE.

Никогда не объединяй run'ы до того, как мысленно разделил смешанные run'ы на элементарные сегменты.

==================================================
6. SPLIT
==================================================

Разделяй run ОБЯЗАТЕЛЬНО, если внутри него есть:

- метка + значение
- части разных классов
- части разных ролей
- явная граница между логическими элементами

Примеры границ:
- двоеточие после метки
- номер
- дата
- служебный маркер
- переход от статической формулировки к значению

Пример:
"Тел.: 8 (727) 269 95 88"

должно стать:
1) "Тел.:" -> template_static / field_label
2) " 8 (727) 269 95 88" -> issuer_profile / issuer_contact

ПРАВИЛА SPLIT:
- не теряй символы
- сумма split-сегментов должна полностью покрывать исходный текст
- start/end в sources обязаны быть точными

==================================================
7. MERGE
==================================================

После split можно объединять соседние text-run в один сегмент ТОЛЬКО если одновременно верно всё:

- они идут подряд в одном абзаце
- между ними нет других видимых элементов
- оба имеют type = "text"
- они принадлежат одному классу
- они принадлежат одной роли
- вместе образуют один логический элемент
- объединение не смешивает метку и значение
- объединение не смешивает разные классы
- объединение не смешивает разные роли

MERGE ЗАПРЕЩЁН:
- между разными абзацами
- между разными классами
- между разными ролями
- если у run разные char_style_id
- если merge ухудшает точность сегментации

ПРИЗНАКИ, ЧТО MERGE НУЖЕН:
- граница проходит внутри слова
- соседние run составляют одну фразу
- соседние run составляют одну метку
- соседние run составляют одно значение

==================================================
8. ПРАВИЛА НУМЕРАЦИИ ID
==================================================

ИСПОЛЬЗУЙ ТОЛЬКО реальные исходные run_id из donor.json.

НЕЛЬЗЯ придумывать искусственные id вида run_4.1, если исходный run_id был p_6.run_1.

8.1. Если run не split и не merge:
id = исходный run_id

Пример:
p_6.run_1 -> p_6.run_1

8.2. Если один run split на несколько сегментов:
id = <исходный_run_id>.<M>

где M = 1, 2, 3 ... слева направо

Пример:
p_6.run_1 -> p_6.run_1.1, p_6.run_1.2

8.3. Если несколько run merged в один сегмент:
id = <first_run_id>.1

Пример:
p_10.run_3 + p_10.run_4 -> p_10.run_3.1

8.4. Если был и split, и merge:
id якорится к ПЕРВОМУ исходному run, с которого начинается итоговый сегмент

ГЛАВНОЕ:
- id = якорь сегмента
- полное происхождение определяется по sources
- id обязан сохранять paragraph/run происхождение

==================================================
9. SOURCES
==================================================

Каждый сегмент обязан иметь sources.

Формат:
{
  "run_id": "p_6.run_1",
  "start": 0,
  "end": 5
}

ПРАВИЛА:
- run_id должен быть реальным исходным run_id
- start включительно
- end не включая
- диапазон должен быть в пределах текста исходного run
- при split указывай точный диапазон внутри run
- при merge перечисляй все участки в правильном порядке
- не используй tab / break / cr / пустые run как source, если они не несут видимого текста

==================================================
10. СПЕЦИАЛЬНЫЕ ПРАВИЛА
==================================================

- Наименование документа обычно является сильным кандидатом на heading
- Если в заголовке есть переменная часть, отделяй устойчивую часть от переменной
- Метка поля и значение поля всегда должны быть разными сегментами
- "М.П." обычно является seal_label, а не seal_text
- Развёрнутый текст печати оценивай по контексту
- Контакты, адрес, реквизиты учреждения обычно issuer_profile
- Персональные данные, даты, номера, значения полей обычно document_dynamic

==================================================
11. ПОЛНОТА
==================================================

ОБЯЗАТЕЛЬНО:
- покрыть все абзацы с видимым текстом
- сохранить порядок абзацев
- сохранить порядок сегментов внутри абзаца
- включить текст внутри таблиц
- не возвращать частичный результат

==================================================
12. САМОПРОВЕРКА ПЕРЕД ОТВЕТОМ
==================================================

Проверь:

1. COVERAGE
Все абзацы с видимым текстом включены.

2. SPLIT
Все split-сегменты полностью покрывают исходный текст без потерь.

3. MERGE
Ни один merge не смешивает разные классы или роли.

4. ID
Все id якорятся к реальным run_id donor.json.

5. SOURCES
Все start/end корректны и в границах исходного текста.

6. ABC
Каждый сегмент согласован с ABC-тестом.

7. SCHEMA
Все обязательные поля присутствуют.
Используются только допустимые class и role.
